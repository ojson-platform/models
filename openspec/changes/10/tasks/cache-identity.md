# cache-identity

Сценарии этой задачи:

- Кэш не даёт идентичность Model без имени
- Пустое имя не получает идентичность
- Кэш без props берёт ключ пустого объекта

Якорь в `design.md`, раздел Technical prerequisites: `Cache.key`, `Cache.update` и стратегии `CacheOnly`, `CacheFirst`, `StaleWhileRevalidate` берут ключ только из ответа `modelIdentity`. Рядом пункт «Флага нет».

`request` и `set` уже спрашивают `modelIdentity` с предыдущей задачи. Здесь они не переписываются. Сценарий «Пустое имя не получает идентичность» всё равно проверяет и их: обращение и предустановка с пустым именем завершаются ошибкой, Model не выполняется.

## Сделать

`Cache.key`, `Cache.update`, `CacheOnly`, `CacheFirst` и `StaleWhileRevalidate` берут ключ и props только из ответа `modelIdentity`, и только до `get` и `set` провайдера.

При отказе (`TypeError` с текстом `Model should define static displayName property`) провайдер не вызывается и Model не выполняется. Это отказ и для отсутствующего имени, и для пустого.

Props не переданы: Model с именем `M` получает пустой объект, результат записывается под ключом `M;`. Повтор в другом запросе с пустым объектом получает этот результат, Model снова не выполняется.

`Cache.key` возвращает строку ключа из ответа и сам props не подписывает. Исполнение Model идёт с props ответа. `NetworkOnly` ключ не строит: он по-прежнему входит через `request`.

Флага нет. После этого поведение выровнено по умолчанию. Текст ключа, который мемоизация, предустановка и кэш уже отдавали одинаковым, не меняется, записи кэша не переписываются.

`withOverrides`, телеметрия, дедлайн и валидация ключ не строят и здесь не меняются.

## Доказательство

Имя каждого теста содержит заголовок своего сценария. Наблюдение — граница `model-identity` в `design.md`: аргументы `get` и `set` хранилища, props которые получает Model, и отсутствие вызова хранилища и Model при отказе. `sign` тестом не вызывается.

Команды: `pnpm run test:units:fast`, `pnpm run test:types`. Уже зелёные тесты предыдущей задачи остаются зелёными.

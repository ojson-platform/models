# Идентичность Model

Одно определение идентичности. Мемоизация запроса (`request`), предустановка (`set`) и межзапросный кэш спрашивают его и не собирают ключ сами. Текст ключа остаётся прежним там, где эти три места уже совпадают: имя, затем `;`, затем запись props через существующий `sign`. Props остаются `OJson`. Мемоизация запроса и межзапросный кэш остаются разными слоями. Реестр одного запроса не делится с другим.

## Verification boundary

### model-identity

Сценарий дельты доказан тестом, в имени которого есть заголовок сценария.

Наблюдение снаружи этого определения:

- ответ идентичности: ключ и props одним значением;
- мемоизация и предустановка: `ctx.request` и `ctx.set` — сколько раз выполняется Model, какие props она получает, находится ли записанное значение;
- межзапросный кэш: аргументы `get` и `set` хранилища и props, которые получает Model. Отказ Model без имени и с пустым именем не вызывает хранилище и не выполняет Model.

`sign` тестом не вызывается. Корень пакета не получает новый экспорт ради доступа к нижнему построению ключа.

Команды: `pnpm run test:units:fast`, `pnpm run test:types`.

## Technical prerequisites

- Код в этом PR. Функция в `src/utils` рядом с `sign` и `cleanUndefined`. Из корня пакета не экспортируется. Вход — Model и props. Ответ — ключ и props, либо отказ.
  - Нет `displayName` или он пустой: `TypeError` с текстом `Model should define static displayName property`. Ключа нет.
  - Props не переданы: пустой объект. У Model с именем `M` ключ `M;`, Model получает пустой объект.
  - В props ответа нет свойств со значением `undefined`, в том числе внутри вложенного объекта. Пропуск свойства и то же свойство со значением `undefined` дают один ответ. `null`, `false`, `0` и пустая строка остаются.
  - Ключ — `displayName`, затем `;`, затем `sign` от props ответа. Порядок свойств ключ не меняет. Кодирование `sign` не заменяется.
- Код в этом PR. `request` и `set` берут ключ и props только из этого ответа. Model выполняется с props ответа. Реестр запроса остаётся своим.
- Код в этом PR. `Cache.key`, `Cache.update` и стратегии `CacheOnly`, `CacheFirst`, `StaleWhileRevalidate` берут ключ только из этого ответа и только до `get` и `set` провайдера. При отказе провайдер не вызывается и Model не выполняется. Исполнение идёт с props ответа. `Cache.key` возвращает строку ключа из ответа и сам props не подписывает.
- Флага нет. Выровненное поведение — значение по умолчанию. После merge записи кэша не переписываются: согласованный текст ключа не меняется.

`withOverrides`, телеметрия, дедлайн и валидация ключ не строят. Они по-прежнему входят через `request` и `set`.
